# F-001 — File Upload & Workspace Import

**Status:** Approved
**Priority:** P0
**Clients:** all
**Depends on:** —
**Related specs:** [03-storage-and-portability](../specs/03-storage-and-portability.md), [04-ingestion-pipeline](../specs/04-ingestion-pipeline.md), [12-reliability](../specs/12-reliability.md), [ADR-0017](../decisions/ADR-0017-resumable-upload-protocol.md), [ADR-0018](../decisions/ADR-0018-workspace-layout-and-adoption.md), [ADR-0019](../decisions/ADR-0019-source-tree-semantics.md)

## Summary

Get files into the system two ways: upload through the API into a chosen workspace path, and import an existing folder hierarchy by pointing a workspace at a subtree of the mounted storage. Both converge on the same result: real files at real paths, registered, hashed, and queued for extraction. Nothing blocks on analysis.

## User stories

- As a user, I want to upload files (including multi-GB videos) into a folder of my workspace so that they are stored and become searchable.
- As a new user, I want to import my existing NAS folder structure as-is so that I can adopt the app without reorganizing anything.
- As a user, I want files I copy onto the NAS directly (outside the app) to show up in the app so that both paths stay usable.

## Functional requirements

- **FR-1** Upload targets a workspace + path; the file is written to that real path on the source storage. Original bytes are stored unmodified.
- **FR-2** Uploads are chunked/resumable; an interrupted multi-GB upload resumes rather than restarts.
- **FR-3** Upload responds as soon as the file is safely stored; extraction is queued asynchronously (`202`-style, job reference returned).
- **FR-4** Import: a workspace can be created over an existing subtree; the scanner registers every file (path, size, mtime, content hash) without moving, renaming, or modifying anything.
- **FR-5** *(verify: fault-injection)* Import at 10 TB scale is resumable and incremental: restarts continue where they left off; progress (files found / registered / extracted) is queryable via API.
- **FR-6** Re-scan reconciles external changes: new file → register + ingest; changed content (hash differs) → new version ([F-007](F-007-versioning.md)); missing file → a trash entry badged "removed outside the app" ([F-014/FR-10](F-014-deletion-and-trash.md)), never silently purged from the index.
- **FR-7** Name collisions on upload are handled predictably (reject or new-version, per explicit parameter; default: reject with clear error). A collision is a clash on the comparison key ([F-015/FR-6](F-015-folders.md)), so uploading `Report.pdf` beside an existing `report.pdf` collides.
- **FR-8** Every registered file is immediately visible in listings with basic file metadata, with extraction status `pending` — searchability by content follows as extractors complete.
- **FR-9** *(removed — superseded by [FR-14](#functional-requirements); the interim `104` it required is out of reach on ASGI, see [Q58](../OPEN-QUESTIONS.md))*
- **FR-10** **Adoption is admin-gated** ([ADR-0018](../decisions/ADR-0018-workspace-layout-and-adoption.md)): creating a workspace over an existing directory requires an admin and a path resolving inside the `SE_ADOPTION_ROOTS` allow-list; a path outside it, a path overlapping another workspace root, or a filesystem failing the `fs-check` probe is refused with a problem response naming the reason. Non-admin callers cannot adopt at all.
- **FR-11** **Scan conflicts are reported, never resolved on disk** ([ADR-0019](../decisions/ADR-0019-source-tree-semantics.md)): when a scan finds sibling names colliding on the comparison key (NFC-normalized, case-folded), the first in traversal order registers and each other is listed as a conflict with both names; no file on disk is renamed, moved, deleted, or overwritten by the app to resolve one.
- **FR-12** *(negative space)* **No path outside the workspace root is ever read or written**: symlinks are not dereferenced by any scan (each is recorded as a skipped entry), and every content read or write re-resolves its path and refuses one that leaves the workspace root — including a dangling link and a link whose lexical path looks contained.
- **FR-13** *(negative space)* The `.workspace/` control directory and everything inside it is **never** registered as a folder or file, returned in a listing, or served as content.
- **FR-14** **Wire protocol** (supersedes [FR-9](#functional-requirements); [ADR-0017](../decisions/ADR-0017-resumable-upload-protocol.md)): the upload endpoint implements the IETF resumable-upload protocol. `OPTIONS` answers `200` with `Upload-Limit` carrying `min-append-size`, `max-append-size` and `max-age`. A creation request carrying `Upload-Complete: ?0` answers `201` with a `Location` naming the upload resource; one carrying `?1` stores the file and answers `201` with a `Location` naming the file. `HEAD` on an upload resource answers `204` with its current `Upload-Offset`. A `PATCH` append carries `Content-Type: application/partial-upload` and answers `204`, or `200` when it completes the upload; at a wrong offset it answers `409` carrying the correct `Upload-Offset` and the registered problem type `mismatching-upload-offset`. `DELETE` answers `204` and discards the staged content. **No interim `104` is sent**: the draft's carve-out for a server that cannot send interim responses applies, and ASGI provides no way to send one ([Q58](../OPEN-QUESTIONS.md)). A request whose `Upload-Draft-Interop-Version` is absent or unsupported is served as an ordinary upload.
- **FR-16** *(negative space)* **"I could not look" is never treated as "it is not there."** A directory the scan cannot read — permissions, a mount that went away, a path that resolves outside the workspace — is reported as a skipped entry and yields no registrations and no deletions; only a directory that is confirmed **absent** says anything about the files the app knows are inside it.
- **FR-15** *(negative space)* **An acknowledged offset is never wrong.** Content is `fsync`'d before the offset that covers it is committed, and a resumed upload discards every staged byte past the committed offset — so no assembled file contains bytes a client did not send, and none is missing bytes an offset claimed. Staging that no longer *covers* the committed offset — truncated or removed under the session, which the user-visible `.workspace/staging/` makes reachable — cannot be repaired: the append is refused with `410`, the session ends, and the client starts a new upload rather than assembling content nobody sent. *(verify: fault-injection)*
- **FR-17** *(negative space)* **A tree that does not identify itself is never reconciled.** A scan whose workspace root carries no `.workspace/marker`, an unreadable one, or one naming a different workspace registers nothing, reconciles nothing and modifies no file: the run ends reporting the reason, and the workspace's schedule stays armed. An unmounted share is indistinguishable from an empty directory by listing alone, so the marker is read before the traversal starts **and again before the run reconciles anything, including before each batch of reconciliation commits** — a walk of ten terabytes lasts long enough for a share to leave in the middle of it, and every directory still on the frontier then comes back absent ([ADR-0018](../decisions/ADR-0018-workspace-layout-and-adoption.md)).
- **FR-18** *(negative space)* **Only an absence concludes a deletion.** A file becomes a trash entry only when the directory that should hold it was successfully listed — or confirmed absent — and did not contain its name. An entry the scan saw and refused (a symlink, the loser of a name collision, a name the policy rejects, an entry it could not `stat`) leaves the file `live` and is reported as a finding instead.
- **FR-19** **A file that only moved keeps its identity.** When a scan finds content at a new path whose hash matches a live file in the same workspace whose own path is confirmed absent, that file's row moves to the new path — same UUID, no registration, no trash entry — and the event records which rule matched. Several candidates are resolved by preferring the one that kept its **name**, then the **oldest registration**; a changed hash is never a move ([02 § file](../specs/02-domain-model.md#file)).
- **FR-21** **A filesystem watcher accelerates detection, and nothing depends on it** ([ADR-0019](../decisions/ADR-0019-source-tree-semantics.md)): where the platform delivers events for a workspace root, a change is coalesced with the burst around it into **one** scan of the directory that covers them, requested through the same operation a manual rescan uses and recorded with trigger `watcher`. Each workspace reports whether it is watched, and why not when it is not, via `GET /workspaces/{ws}/import-status`. *(negative space)* **No change is ever noticed only because a watcher fired**: absence, a refused subscription (a kernel watch limit, a permission, a mount that delivers no events) and event loss are not error conditions — they cost latency, the scheduled pass reaches the same state, and no file is registered, versioned or trashed by a watcher event that the same scan would not have done on its own.
- **FR-22** *(negative space)* **A mount that went away is never reconciled as a deletion.** A scan records the filesystem (`st_dev`) of every directory it lists. A directory that is readable and **empty**, whose filesystem differs from the one recorded for it, and beneath which the index still holds at least one `live` file, is treated exactly as an unreadable one ([FR-16](#functional-requirements)): no registrations, no deletions, no folder-identity transfer, and a finding naming the path and the reason. Its recorded filesystem is left unchanged while that holds, so the subtree is reconciled again — with no operator action — on the first scan that finds the recorded filesystem back. The root marker ([FR-17](#functional-requirements)) cannot cover this: a mount point below the root whose mount is gone is a readable, empty directory on the parent's filesystem, so nothing in a listing distinguishes it from a directory somebody emptied.
- **FR-20** **An overwrite never destroys content the app has not recorded.** An upload with `if_exists=new_version` copies the current content into the app-owned `versions/` area *before* writing, and is refused with `409` if what it copied does not match the version it means to supersede — the file changed on the storage and a re-scan has to record that first. The destination path holds valid content at every instant of the exchange. Content the app has **never registered** is refused rather than replaced: a file that arrived on the storage since the last scan, or one a scan reported instead of registering, is not a collision any row can describe, so an upload onto it answers `409` naming the path and leaves the bytes alone — a re-scan has to record them first.

## API surface

`POST·OPTIONS /workspaces/{ws}/files` (upload creation, `Upload-Limit`, `if_exists=reject|new_version`) · `HEAD·PATCH·DELETE /uploads/{id}` (offset, append, cancel) · `POST /workspaces` (with `adopt_path`, admin) · `POST /workspaces/{ws}/rescan` (whole workspace or a subtree) · `GET /workspaces/{ws}/import-status` (incl. scan conflicts, skipped entries, what each run changed, moved, trashed and restored, and whether the root is watched) · `GET /files/{id}` (incl. extraction status, and why a file is in the trash)

## Out of scope

Desktop sync clients, WebDAV (deferred; see [08-api-principles](../specs/08-api-principles.md) for the primitives that keep them possible). ## Acceptance criteria

- **AC-1** (FR-2, FR-14, FR-15) A 4 GB upload is interrupted mid-body and resumed: `HEAD` reports the committed offset, the client appends from there, and the stored file's SHA-256 equals the source's. A `PATCH` sent at a stale offset answers `409` with the current offset, and the file is not corrupted by it. Killing the process between an append's `fsync` and its offset commit, then resuming, yields the same file — the re-sent chunk appears once.
- **AC-2** (FR-14) `OPTIONS` on the upload endpoint answers `200` with `Upload-Limit`; a creation request declaring interop version 9 and `Upload-Complete: ?0` receives `201` with a `Location` naming the upload resource; the same request with no interop-version header and no `Upload-Complete` stores the file and answers `201` with a `Location` naming the file.
- **AC-3** (FR-4, FR-5) Importing a subtree with 100 000 files registers all of them; killing the importer at each injected fault point and restarting yields the same final state, with no duplicate registrations and no debris past the grace window ([12 § verification](../specs/12-reliability.md#verification)).
- **AC-4** (FR-6) A file copied onto the storage by hand appears after the scheduled scan with correct path and queued extraction; an externally modified file yields a new version; an externally deleted file becomes a trash entry badged "removed outside the app" and is never silently dropped from the index.
- **AC-5** (FR-10) A member's attempt to adopt any path is refused; an admin adopting a path outside `SE_ADOPTION_ROOTS`, or overlapping an existing workspace root, is refused with the reason named; an admin adopting an allow-listed directory indexes it with **zero** bytes copied and zero entries renamed.
- **AC-6** (FR-11) A tree containing `Report.pdf` and `report.pdf` as siblings, plus an NFC/NFD pair of one name, imports one of each and lists the others as conflicts naming both spellings; a byte-for-byte comparison of the tree before and after the scan shows it unchanged. *(The collision can only exist on a case-sensitive, byte-preserving filesystem, so the end-to-end case is asserted where the filesystem allows it and the rule itself is asserted from the classifier's inputs everywhere.)*
- **AC-11** (FR-16) A directory whose permissions deny reading is reported as skipped, and the files the app already knows inside it keep their state; the same directory, deleted instead, is reported as missing.
- **AC-7** (FR-12) A symlink to `/etc/passwd` and a symlink to a directory outside the workspace are both recorded as skipped, appear in no listing, and their targets are never read; requesting content through a path that resolves outside the root is refused.
- **AC-8** (FR-13) After an upload and a scan, no listing, search, or content endpoint returns `.workspace`, its `marker`, or any staging entry.
- **AC-9** (FR-1, FR-4) No import or upload path ever modifies an original file's bytes or location — asserted by hashing every fixture before and after a full import plus an upload into the same tree.
- **AC-12** (FR-17) With the workspace root emptied of its control directory — what an unmounted share looks like — a re-scan registers nothing, trashes nothing, and reports the missing marker as the reason; the same root carrying another workspace's marker is refused naming that workspace. Both leave every known file `live`.
- **AC-13** (FR-18) A registered file replaced on disk by a symlink of the same name stays `live` and is reported as a skipped entry; only a name absent from a directory the scan read produces a trash entry.
- **AC-14** (FR-19) A file moved to another directory on the storage keeps its UUID, produces no trash entry and no registration; a directory of byte-identical files renamed on the storage re-matches every file by name, so all of them move; a copy — the original still present — registers a new file instead.
- **AC-16** (FR-21) A file copied into a watched workspace produces one queued scan of the directory it landed in, triggered `watcher`, and the file is registered by it; a workspace whose subscription the kernel refuses reports `unavailable` with the limit named, keeps its schedule, and still imports the same file on the next scheduled pass; with the watcher disabled, nothing is subscribed and nothing is queued; and writes into `.workspace/staging/` — the app's own upload chunks — queue nothing at all.
- **AC-17** (FR-17) A share removed the instant the traversal ends — every directory listed, nothing reconciled yet — ends the run refused, with zero trash entries and every known file `live`; a share removed while the sweep is running loses only the batch in flight, which is rolled back rather than committed.
- **AC-18** (FR-22) A directory whose recorded filesystem differs from the one it is on now, emptied of the files the index holds beneath it, is reported as skipped, produces zero trash entries and leaves those files `live`; the same empty directory on its recorded filesystem produces a trash entry for each of them.
- **AC-15** (FR-20, [F-007/FR-9](F-007-versioning.md)) Uploading with `if_exists=new_version` over an existing file yields two versions whose predecessor's bytes are byte-identical in `versions/` and marked restorable, and the source tree shows exactly one file at that path; the same upload against a file edited on disk since the last scan answers `409` and changes nothing; the default (`reject`) answers `409` and leaves the file untouched.
