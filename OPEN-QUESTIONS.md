# Open Questions

| Q1 | **What exactly is a workspace?** → A workspace corresponds to a **top-level folder** with a *(source type, location)*: `local` = read+write, `external` (GDrive, …) = read-only, fully mirrored onto the server. | Q12 | **Upload/file-request links.** Should share links also support *receiving* files from account-less visitors? (pCloud/Drive have this; not discussed yet.) | 🔴 |
| Q13 | **Backup & restore story.** Much still to discuss — must be resolved before v1 ships ([10](specs/10-deployment-and-operations.md#backups--restore)). **What:** PostgreSQL (all manual/authoritative data) and `versions/` (the only copy of superseded originals) are mandatory; the derived store is regenerable but re-deriving 10 TB costs weeks of CPU — back it up anyway?; `.env`/config. The source tree is the user's own responsibility (document loudly). **When:** schedule; always before upgrade/migration (Q20). **How:** `pg_dump` vs. physical/WAL; DB and file areas together or separately; consistency across DB ↔ `versions/` ↔ derived store (snapshot ordering). **Restore:** documented + periodically exercised — an untested restore is not a backup. Retention. | 🔴 |

| Q18 | **WebSocket authentication mechanism** ([F-012](features/F-012-live-updates.md)). | Q20 | **Migration execution on upgrade.** Migrations are versioned, expand–contract, tested up+down ([10](specs/10-deployment-and-operations.md#upgrades--migrations), [11](specs/11-engineering-standards.md)); rollback = redeploy the previous image. | Q21 | **Share links to trashed files: 404 or 410?** While a file is trashed its links are suspended, not revoked ([F-014/FR-11](features/F-014-deletion-and-trash.md)). `404` leaks nothing (deletion state is content-derived information); `410` is semantically honest and matches expired/revoked links ([08](specs/08-api-principles.md#errors-rfc-9457)). Decide before implementing share-link serving. | 🔴 |
| Q22 | **Symlinks in source trees.** Follow, skip, or record-as-such — affects ingestion/re-scan ([F-001](features/F-001-upload-and-import.md)), folder reconciliation ([F-015](features/F-015-folders.md)), and archive building ([F-016](features/F-016-archive-download.md)). | Q23 | **Folder-tag inheritance to contents.** v1 folder tags are self-only ([F-015/FR-9](features/F-015-folders.md)). | Q25 | **File/folder name case policy.** Options: case-insensitive-unique + case-preserving (matches SMB/macOS/Windows and future sync clients; needs a conflict path when importing Linux trees containing case-colliding siblings; case-only rename = rename) · case-sensitive exact (Linux-native, no import conflicts; unpredictable over SMB, painful for future sync) · follow-the-filesystem (per-deployment behavior, doubled test matrix — advised against). | Q32 | **NAS filesystem guarantees.** The write protocol ([12](specs/12-reliability.md#filesystem-write-protocol)) leans on atomic `rename` and honest `fsync`; SMB/NFS mounts weaken both in mount-option-dependent ways. | Q33 | **Operation-table hygiene & history retention.** Millions of terminal job rows degrade the hot claim query; terminal rows move to a history table or are pruned ([12](specs/12-reliability.md#queue-hygiene)). | Q35 | **Map tile sourcing.** The map page ([F-017](features/F-017-views.md)) needs base-map tiles; the default deployment promises zero external calls ([00](specs/00-vision-and-goals.md#security-posture)), and a browser fetching third-party tiles leaks coarse viewing locations to the provider.
