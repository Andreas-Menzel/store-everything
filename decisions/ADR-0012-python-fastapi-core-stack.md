# ADR-0012 — Core service stack: Python + FastAPI, PostgreSQL via SQLAlchemy Core

**Status:** Accepted
**Date:** 2026-08-20

## Context

[Q10](../OPEN-QUESTIONS.md) asked for the language and framework of the core API service and orchestrator, with four criteria: a strong PostgreSQL story, async job handling, WebSockets, and comfortable long-term maintenance. No code could be written before it was answered.

Two structural facts shrink the technical distance between the candidates:

- **No machine learning runs in the core.** Every model executes inside an extractor container behind a fixed API ([ADR-0002](ADR-0002-extractor-containers-fixed-api.md)). A survey of comparable self-hosted products confirms this as the dominant pattern — Immich runs its models in a separate Python/ONNX service; PhotoPrism's in-process CGo TensorFlow bound it to a stale 1.x branch for years. The core's own work is HTTP, SQL, filesystem IO, and job orchestration.
- **The reliability substrate is hand-written SQL in every candidate** ([ADR-0013](ADR-0013-owned-operation-layer.md)): guarded compare-and-swap transitions, `FOR UPDATE SKIP LOCKED` claims, heartbeat leases, outbox writes ([12](../specs/12-reliability.md)). No framework abstracts that away; each language would execute the same statements.

Comparable products in this category run on Go (PhotoPrism, Ente, Photoview, Filestash), TypeScript/NestJS (Immich), and Python/Django (Paperless-ngx, LibrePhotos). All three ecosystems satisfy criteria one through three. The deciding criterion is therefore the fourth: who maintains this for years, and in which language are they fastest and most correct.

Go was evaluated as the strongest *technical* fit — typed SQL access, a single static binary, the lowest memory floor, and an embeddable IETF resumable-uploads implementation (`tusd`) that would have pre-solved [Q38](../OPEN-QUESTIONS.md). It was not chosen: the maintainer's fluency is in Python, and for a project whose principal risk is decade-long maintenance by a one-to-two-person team, fluency outweighs a constant-factor runtime advantage on workloads the specs already permit to be slow ([00 § scale and performance targets](../specs/00-vision-and-goals.md#scale-and-performance-targets): ingestion may take minutes to hours; search latency is PostgreSQL-bound).

## Decision

We will build the core service and orchestrator in **Python 3.13 with FastAPI**, accessing PostgreSQL through **SQLAlchemy 2 Core and hand-written SQL — without an ORM session layer**.

The concrete toolchain, fixed here so it is enforceable in CI:

| Concern | Choice |
|---|---|
| Runtime & dependencies | Python 3.13; **uv** for resolution, locking, and virtualenvs; lockfile committed ([11 § dependencies](../specs/11-engineering-standards.md#dependencies--configuration)) |
| HTTP | **FastAPI** on uvicorn; **Pydantic v2** request/response models with `extra="forbid"` — the unknown-fields rejection [08](../specs/08-api-principles.md) requires |
| Database access | **psycopg 3** (async) + **SQLAlchemy 2 Core**: table metadata as the single schema truth, composable query construction, connection pooling. **No ORM session** — no identity map, no dirty tracking, no autoflush |
| Migrations | **Alembic**, autogenerated against the Core metadata, reviewed by hand; up **and** down tested in CI ([10 § upgrades](../specs/10-deployment-and-operations.md#upgrades--migrations)) |
| Lint / format / types | **ruff** (lint + format), **pyright** in strict mode — both blocking |
| Tests | **pytest** + pytest-asyncio; **testcontainers** for a real PostgreSQL + pgvector; **hypothesis** for the property-based invariants [11](../specs/11-engineering-standards.md#testing) requires |
| Traceability | FR markers as `@pytest.mark.fr("F-002/FR-7")`, consumed by the matrix generator ([11 § matrix](../specs/11-engineering-standards.md#requirement-traceability-the-matrix)) |
| Deployment unit | the Docker image ([ADR-0005](ADR-0005-single-server-docker-network.md)) — not a binary |

**Why no ORM session.** The two heaviest data-access surfaces in this system are the reliability substrate and search. Both need exact control over which statements run, in which transaction, in which order — a lease claim is `UPDATE … WHERE state = $expected AND attempt = $token`, and search is FTS plus pgvector plus permission joins plus rank fusion ([06](../specs/06-search.md)). A Session's value proposition is precisely the implicit layer that would sit in between: autoflush deciding when SQL is emitted, an identity map serving a stale object after a lost compare-and-swap. Those are the failure modes [ADR-0010](ADR-0010-crash-only-execution-model.md) exists to exclude. Sessions would then earn their keep only on trivial CRUD — leaving two data-access idioms in one codebase, against [11 § code reuse](../specs/11-engineering-standards.md#code-reuse--shared-modules). We keep SQLAlchemy's typed metadata, query builder, and pooling, and drop object-graph change tracking, which this system never needs: rows map to Pydantic models at the API boundary. Immich made the same move for the same reasons when it replaced TypeORM with a query builder.

## Consequences

- **CPU-bound work must stay out of the core.** Analysis lives in extractors by architecture; hashing and IO release the GIL in C code. Any future in-core hot loop is a design smell to be pushed into an extractor or a background process, not solved with threads.
- **We implement the resumable-upload wire protocol ourselves.** No mature Python server implementation of the IETF resumable-uploads draft exists; Go's `tusd` would have shipped it. The protocol is small and the work lands in phase 1 with [F-001](../features/F-001-upload-and-import.md); [Q38](../OPEN-QUESTIONS.md) now decides only the format, not the library.
- **Dynamic typing is compensated by gates, not by convention:** pyright strict and boundary validation are blocking CI steps, so type discipline cannot erode quietly.
- **Two languages live in the repo** (Python core, TypeScript web — [ADR-0014](ADR-0014-vue-frontend-stack.md)). The only shared contract between them is the generated OpenAPI client; no types are shared by import.
- **Reversibility is preserved where it matters.** The durable assets are the HTTP contract ([08](../specs/08-api-principles.md)) and the SQL schema, not the framework: a future core rewritten in another language serves the same OpenAPI document against the same database, and the extractor contract never knew the core's language to begin with.
- Resolves [Q10](../OPEN-QUESTIONS.md).
