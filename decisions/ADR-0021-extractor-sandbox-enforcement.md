# ADR-0021 — Extractor sandbox: egress-less compose services, per-job HTTP file access

**Status:** Accepted
**Date:** 2026-08-23

## Context

Extractors run third-party-installable code against every byte a user stores, and the deployment promises **no outbound network by default** ([00 § security posture](../specs/00-vision-and-goals.md#security-posture), [05](../specs/05-extractor-contract.md#container-requirements-hardening)). Q7 asked how that is enforced, what an extractor may mount, and how an admin sees a network-enabled one. The threat model is double: a malicious or compromised extractor image, *and* a benign extractor compromised by hostile content (a crafted PDF exploiting the parser). Either way the blast radius must exclude the database, the source trees, other extractors' work, and the internet.

What the survey found (2026-08): the standard resolution of "core↔extractor yes, extractor→world no" is a Docker network with `internal: true` — no gateway, so no egress, while members still reach each other. Two engine facts qualify it: before Moby 25.0.5, the embedded DNS forwarded lookups from internal networks to the host resolver — a data-exfiltration channel (CVE-2024-29018); and Docker Engine 28 additionally drops unsolicited LAN traffic to container IPs. Runtime container management is the other lesson: every system that lets a core spawn containers ends up interposing a guarded socket proxy and still treats the socket as its riskiest surface (Nextcloud ExApps' trajectory), while Immich, Paperless-ngx, and Frigate simply pre-start analyzers as services. Immich's own docs describe its ML sidecar as having "no security measures whatsoever" — the bar to clear is low, and we intend to clear it by construction.

## Decision

1. **Extractors are long-running Compose services.** The core never talks to the Docker API: no `docker.sock` anywhere in the stack (the phase-1 containers already run `cap_drop: [ALL]`, `no-new-privileges`, non-root), no socket proxy, no dynamic container lifecycle. Installing an extractor = adding a compose block from the shipped template; official extractors ship as a compose include.
2. **One dedicated `extractors` network, `internal: true`.** Each extractor joins **only** it; the core API service joins it additionally. An extractor can reach exactly one thing — the extractor API ([ADR-0020](ADR-0020-extractor-dispatch-and-wire-protocol.md)) — and nothing else: not PostgreSQL, not Traefik, not the internet. Egress is denied by topology (no gateway), not by in-container policy. Extractors run no listeners (poll dispatch), so extractor-to-extractor reachability on the shared network has nothing to reach.
3. **File access is per-job HTTP references only — no mounts.** Neither source trees nor the app-data volume are ever mounted into an extractor. The job payload carries input references resolved as Range-capable URLs on the extractor API, scoped to that job; an extractor sees exactly the bytes of work routed to it, and a compromised image cannot sweep the library. This also keeps the contract location-agnostic — a remote extractor resolves references identically. The cost — inputs stream once through the core over the local bridge — is accepted at this scale; a same-host scratch-directory handoff for very large files is recorded as a possible later optimization (Q60), not built now.
4. **Hardening template** for every extractor service, shipped in the compose include and required for third-party entries by the operator docs: `read_only: true` root filesystem · `tmpfs` scratch (sizing documented per extractor; disk-backed scratch volumes are the documented variant for large-input extractors) · `cap_drop: [ALL]` · `security_opt: [no-new-privileges:true]` · non-root user · `pids_limit`, memory and CPU limits · short `stop_grace_period` (leases make hard stops safe). Official images follow the same baseline as the core: non-root, digest-pinned base, dependency- and image-scanned in CI ([05 § container requirements](../specs/05-extractor-contract.md#container-requirements-hardening)).
5. **Network-enabled extractors are an explicit, visible exception.** A manifest declaring `network: outbound` (remote-AI extractors — Q19) additionally joins an explicit egress-capable network in compose. The registry surfaces the declared flag in the admin extractor list; the deployment docs pair the flag with the compose change so intent and enforcement are reviewed together.
6. **Honesty about the enforcement point.** The core enforces what it can observe: token-scoped claims, per-job input scoping, hash-verified result staging, fenced writes. The *egress* promise is enforced by compose topology; the core cannot verify a container's networking from inside. So the guarantee is stated where it lives: the shipped template is the enforcement, CI proves it (the sandbox negative test runs the reference extractor under the template and asserts the outside world is unreachable while claims still work), and the conformance kit runs candidate images inside the same harness.
7. **Host floor:** Docker Engine ≥ 25.0.5 (the CVE-2024-29018 DNS fix), 28.x recommended; documented in the install guide as a requirement, since an older engine silently weakens the no-egress promise.

## Consequences

- No per-job cold-start isolation — a long-running extractor that parses hostile content should fork per file internally (Tika's child-process model; extractor-author docs say so). The contract's crash story already covers the failure: a killed worker's lease expires and the job re-runs.
- "Adding an extractor" stays a compose edit plus one minted token — no orchestration platform, no socket exposure, and the admin can audit the entire attack surface by reading one file.
- The sandbox negative test and the engine floor become permanent CI/docs obligations ([ROADMAP § cross-phase tracks](../ROADMAP.md#cross-phase-tracks)).
- Development on Docker Desktop differs from production Engine (Desktop-only escapes like CVE-2025-9074 exist); the docs state that the promise is evaluated against the production Engine deployment.
- [10 § topology](../specs/10-deployment-and-operations.md#topology) is corrected in the same change: extractors previously read as living on the shared internal network, which would have let them reach PostgreSQL.
